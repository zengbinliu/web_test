# XMind + 需求文档 → 禅道测试用例

## 必须先读

1. 禅道 MCP 能力、工具参数与附件分工：阅读 `~/.cursor/skills/zentao-mcp/SKILL.md`。
2. 网页附件上传（`file/ajaxUpload`、`imgFile`、Cookie 会话）：需要脚本或排错时阅读 `~/.cursor/skills/zentao-api/` 下说明与 `scripts/upload_testcase_via_edit_form.py`。
3. 调用 MCP 前不确定参数时：读工作区 `.cursor/projects/*/mcps/user-zentao-mcp/tools/*.json` 中对应工具的 JSON Schema。

**禁止**在本技能或仓库正文中写入禅道账号、密码、Cookie；使用环境变量或本机临时文件，用后删除。

## 导图约定（与业务对齐）

| 节点前缀 | 含义 | 用例化方式 |
|----------|------|------------|
| `m:` | 模块（层级路径） | 映射为标题中的「模块-模块-模块」路径片段 |
| `l:` | 逻辑 | 需将逻辑，根据用例设计原则，结合建立的本地知识库，思考出测试点。为每条**独立**用例的测试点来源 |
| `p` | 截图挂点 | 其子节点中的 `image.src`（`xap:resources/xxx.png`）对应用例**附件** |

解析 XMind：将 `.xmind` 复制为 `.zip` 解压，读取 `content.json`（或解析 `content.xml`）。图片文件在解压目录 `resources/` 下，文件名与 JSON 中 `resources/` 后路径一致。

## 标准工作流（顺序执行）

1. **建立本地知识库**  
   - 阅读 `content.json` 中目标 sheet（如 `m:前台` 分支）全部 `l:`。  
   - 需求为 PDF 时尝试抽取文本；若编码乱码则以导图 + 可拷贝片段为准，并在交付说明中标注 PDF 未完全解析。
- 并生成知识库文件在(~/ `.cursor` 下)
  
2. **生成测试点**  
   - 按导图 `l` 逻辑以及步骤1的本地知识库，结合等价类划分法、边界值分析法、场景法生成测试点；**一个测试点一条用例**（不可把多个独立断言塞进一条用例标题）。  
   - 示例：「同一账号仅一个主套餐」→ 测试点1：首次购买成功；测试点2：第二次购买失败（独立用例）。

3. **编写用例并写入禅道**  
   - 使用 MCP `zentao_parse_testcase_link` 解析用户给的浏览 URL，得到 `product`、`module`。  
   - 使用 `zentao_testcase_create` 创建；**实质性修改**用 `zentao_testcase_update`（同步给出完整 `steps`，避免只改标题丢步骤）。  
   - **步骤与预期**：条数一致、逐步一一对应、因果关系清晰；每步≤8 步为宜。  
   - **预期**：写可验证结果；文案类须列出应出现的**中英文关键词或完整短句**（如按钮 `Subscribe`、提示含 `declined`、`当前周期不可取消` 等），避免仅写「文案正确」。

4. **附件**  
   - 每个 `p` 下所有图片上传到**对应用例**（与导图逻辑最近的父级 `l` 或独立用例）。  
   - 优先走禅道 21+：`POST .../index.php?m=file&f=ajaxUpload&uid=...&objectType=testcase&objectID=<用例ID>`，表单文件字段 **`imgFile`**；`uid` 从用例编辑页解析。  
   - 可执行仓库技能脚本：`zentao-api/scripts/upload_testcase_via_edit_form.py`，设置 `ZENTAO_URL`、`ZENTAO_ACCOUNT`、`ZENTAO_PASSWORD`，可选 `ZENTAO_WEB_COOKIE`（浏览器整段 Cookie）。  
   - MCP `zentao_testcase_update` 的 `files` 若实例不可用，不要依赖其作为唯一上传路径。

## 用例标题格式（团队约定）

```
【<产品短标题前缀>】<一级模块>-<二级模块>-<三级模块>，<单一测试点简述>
```

- 一级模块：导图顶层业务域（如 `前台`、`后台`）。  
- 二、三级：沿 `m:` 路径向下截取到能区分场景为止；不足三级可用二级 + 功能点名。  
- **单一测试点**：标题只描述本用例验证的一件事（动词开头：验证 / 检查）。  
- 若用户不要求前缀，可省略 `【…】`，但与历史用例并存时建议保留以便检索。

## 用例设计原则

- **等价类划分**：对每个输入项考虑有效/无效等价类
- **边界值分析**：对数值范围、长度限制等设计边界用例
- **场景覆盖**：正向流程 + 异常流程 + 边界场景，必须覆盖思维导图所有的节点
- **独立性**：每条用例只验证一个功能点
- **逻辑优先级**： 以思维导图为准

##  用例类型分类
- 功能测试、接口测试、UI测试、兼容性测试、性能测试、安全测试

## 优先级与类型（参考）

| 优先级 | 含义 |
|--------|------|
| P1 | 核心流程、阻塞 |
| P2 | 重要、高频 |
| P3 | 一般、异常 |
| P4 | 边缘、展示类 |

`type` 与禅道 MCP 枚举一致：`feature` / `interface` / `performance` / `unit` / `system` / `config`；UI 为主仍可用 `feature`，纯 API 用 `interface`。

## 交付物检查清单
